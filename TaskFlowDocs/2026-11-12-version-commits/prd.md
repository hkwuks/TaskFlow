# 仓库代码版本提交与回退点
> Task version: v1
> Status: checking

## Goal

保证 Git 仓库的每个有代码迭代的 TaskFlow 任务版本至少有一个包含该版本仓库改动的提交，以便溯源和回退；根据改动影响适时增加聚焦提交。

## Task Kind

- Kind: capability

## Background / Confirmed Facts

现有版本工具仅检查选定任务文档，完成流程不检查仓库代码提交。用户明确检查范围是整个仓库，不是仅检查任务文档。

## Requirements

- 对所有使用 Git 的 TaskFlow 开发任务，以任务版本作为最低检查边界。
- 有仓库代码或运行配置等开发改动的版本，在进入下一版本或完成前至少有涵盖该版本改动的提交；任务文档提交不能单独充当代码提交。
- 基于改动影响合理增加提交；不自动提交或推送，不纳入不属于任务的改动。
- 当前任务目录与 Todo 的 TaskFlow 任务记录可免提交；仓库其他路径的改动（包括 README、配置及设计文档）均按用户确认的保守规则纳入检查。没有其他路径改动的版本无需空提交。检查无法确定时明确提示，不凭任务文档内容宣称代码已提交。
- 检查整个仓库的已提交和未提交变更，包含暂存与未跟踪文件；保留已有用户文件和任务数据。

## Acceptance Criteria

- 版本切换与任务完成路径能发现缺失代码提交或尚未提交的仓库开发改动，并在操作前阻止。
- 已提交开发改动可通过；纯设计版本可通过；纯文档提交不能冒充代码提交。
- 不依靠文件扩展名判断代码；对无法自动归属的变更提供清晰可核验的处理方式，不静默放行、不自动提交用户改动。
- 自动化验证覆盖多版本、已提交和未提交文件、纯设计版本以及边界和失败场景。

## External Facts

- Depends on external facts: no
- Why not: 任务生命周期由 `hooks/task`、`hooks/version` 和 `hooks/archive` 决定；提交边界由用户确定并以本地 Git 状态验证。

## In Scope

仓库级版本回退点、阶段检查、工作流说明与测试。

## Out of Scope

自动提交、推送、重写历史、对已有任务历史追溯补造提交。

## Risks / Deferred Items

Git 本身不能自动判断改动归属或文件语义；需要明确基线和对不确定情况的可审计处理，不能将任意提交视为充分证据。

## Open Questions

无。2026-11-12 用户确认仓库其他路径的设计文档也按保守规则要求提交。
