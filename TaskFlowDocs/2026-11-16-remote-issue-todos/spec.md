# Spec — 远程 Issues 待办
> Task version: v1
> Status: in_progress

## 目标与成功标准
实现 PRD 所列 GitHub、GitLab 多仓库 Issue 待办及 TaskFlow 生命周期；远端是待办主记录，本地保存执行关联和用户选择的只读快照。

## 架构边界与职责
- 用户操作层选择模式、仓库、Issue 和明确请求的操作；不在后台触发同步。
- 远程访问层负责各平台实例鉴权、分页、Issue 标识、读写与错误分类；不得输出或持久化凭据。
- TaskFlow 生命周期层管理本地任务及其关联，不把远端内容复制成第二份待办主记录。
- 存储和恢复边界需明确项目共享连接配置、本地关联以及跨本地／远程部分成功后的重试。

## 受影响范围
- `skills/taskflow/` 与 `hooks/`：插件用户的入口、生命周期和行为，而非仅修改本仓库治理规则。
- `TaskFlowDocs/todo.md` 的读取、提升、归档、恢复、冲突及检查路径；两份 README、运行时文档和相关测试。
- `hooks/task`、`hooks/archive`、`hooks/reopen`、`hooks/summarize-state`、`hooks/todo-check` 等依赖的具体调整，待设计核查后确定。

## 接口、数据流与契约
- 项目配置记录默认模式及多个平台、实例和仓库标识；每条记录保留实际归属，绝不包含访问令牌。
- 切换默认模式只改变新建条目的默认位置；已有条目继续按原位置处理，用户可选择条目逐条迁移。
- 用户可选择保留带抓取时间的本地只读快照；离线时标为可能过期，不允许把快照当作可编辑主记录。
- 唯一身份至少包含平台、实例、仓库和 Issue 标识；不能把不同仓库的相同编号视为同一项。
- 查询汇总保留来源，并区分完整结果与部分失败；GitHub 列表排除 Pull Request。
- 创建由用户指定目标；编辑基于新读取的远端状态，仅修改用户指定字段；处理并发修改，保留非 TaskFlow 标签。
- 阶段以专用标签表达；完成或取消关闭 Issue。具体标签命名、状态映射、冲突检测与恢复协议待设计。
- 旧本地条目只在用户选择时迁移，保留原文件并关联去重。远端迁回本地时用户明确选择复制及解除关联，远端 Issue 不自动关闭或删除。
- 本地任务与远端 Issue 分属两套存储；先持久化恢复意图和操作标识，再发起远端变更，保存已确认结果后更新本地关联。结果不明时停止自动重试并引导查询核对；不能凭网络失败断定远端未执行。
- 更新时先重新读取远端；当平台支持安全的条件更新时使用条件更新，否则明确并发窗口，检测到冲突或不能确认结果时停止并要求核对，不以先读后写宣称完全无竞态。

## 不变量、错误和恢复
- 默认本地模式；远程更新失败不得伪报成功或丢失本地数据。
- 远端成功但响应丢失、本地写入失败、读取权限不足、远端变更和重复重试均须有明确处理和验证，不得假定本地和远端可原子提交。
- 不记录凭据；Issue 内容和自托管地址按用户授权范围处理。

## 测试约束
- 两平台各覆盖列表分页、创建、更新、标签、状态、权限和失败恢复；覆盖多实例及同号 Issue、迁移重复执行、已有本地模式、归档与恢复。
- 使用可控测试服务或隔离夹具验证网络故障和并发；真实托管服务验证须明确测试资源和授权，不能以模拟替代已完成的真实测试声明。

## 开放设计问题
- 在平台约束下完成阶段标签和恢复协议的细化；无条件更新时按用户接受的竞态限制实施。
- 认证工具选择及未安装或不支持实例时的提示；主机支持范围与依赖约束。
- 远端 Issue 被第三方关闭、删除或转移后的细节和平台能力差异。
## 已核实的接口约束与待审方案
- 使用现有宿主的 `gh api` 和 `glab api` 作为候选适配器；按配置的主机明确寻址，使用标准输入传递请求体，不读取或保存用户令牌。缺少 CLI、对应主机登录或权限时明确报告。
- GitHub 的 Issue 列表含 Pull Request，必须过滤；GitLab 使用 URL 编码项目路径及项目内 IID。多仓库结果包含完整来源，某个来源失败时必须明确标示不完整。
- GitLab 的 `add_labels` 在标签不存在时可能创建项目标签，建立阶段标签时必须把这种副作用和所需权限纳入设计；用户未请求的其他标签不得用整表替换方式清除。
- GitHub 普通写入不支持通用条件请求；预读取和事后核对不能保证阻止两个客户端竞态。用户已接受这一限制，操作提示须明确说明；GitLab 的条件更新能力尚未得到证实。
- 对创建结果不明的操作，持久记录非敏感操作标识及目标，停止自动重试；只有可靠核对后才关联已有 Issue 或由用户决定下一步，不能简单以标题匹配判定唯一。
- 缓存和恢复记录可能包含私有项目信息；默认不生成内容快照，用户显式启用时说明保存位置、访问边界、更新时间和不完整状态，凭据不入文件。
## 操作约定
- 显式操作命令使用项目本地配置与结构化输入；不信任远程字段、转义序列或可执行文本，不执行从 Issue 或配置中读取的命令。GitHub 与 GitLab 适配器只接受校验过的平台、主机和仓库参数。
- 本地模式继续使用现有任务接口；远程模式对已提升任务保存可稳定定位 Issue 的关联。模式切换只影响新建默认值，查询汇总本地遗留项和已连接远端并按关联去重。
- 操作恢复记录保存在不含凭据的项目工作区私有位置；意图与每次远端写入结果分别记录。创建结果未知时不自动重复写入，显式查询和用户确认后恢复；查询不完整时保持未知。
- 每一阶段映射为单一 TaskFlow 专用标签；以增删指定标签的方式更新，保留其他标签。缺失标签的创建及权限要求在操作前提示，更新失败时不假报完成。
- 用户选择生成的只读快照默认不生成；当网络失败时仅作为有时间标记的历史信息展示，且不能作为写入依据。快照及本地恢复材料可能包含私有 Issue 信息，写入之前说明位置和共享风险。
- 对于远端不存在、无权限或已转移，保留本地任务和关联并报告无法确认；不存在与无权限不可由单次 404 安全区分。
- 手工验证基线：`git diff --check`；核心行为由 `bash hooks/smoke-test`、新增聚焦测试和 `powershell -File hooks/smoke-test-windows.ps1` 的相应范围验证；CI 验证 Ubuntu、macOS、Windows。
- 测试文件与入口按现有 `hooks/test-*` 和 `hooks/smoke-test` 约定；插件 hooks 的 Bash 3.2 与无语言运行时约束见 `skills/taskflow/references/runtime.md`。
## 持久数据和恢复协议
- 项目配置使用 `TaskFlowDocs/remote-todos.conf`：首行声明 `local` 或 `remote` 默认模式，其余行声明每个连接的唯一别名、平台、HTTPS 主机和仓库路径；禁止换行、控制字符、URL 用户信息及查询参数，拒绝重复别名。模式缺省时视为本地；连接变更不迁移条目。
- Issue 的稳定身份由平台、规范化主机、平台项目标识和 Issue 编号组成；展示别名不作为唯一身份。GitLab 的项目路径按 API 规定 URL 编码，GitHub 仓库按 owner/repo 校验。
- 只为已提升或显式迁移的条目在本地保留关联；远端未提升 Issue 不生成本地 Todo 正文。关联中保留远端身份和任务路径，不把远端内容设为本地权威。历史本地条目原文保留，通过关联去重。
- 远端创建前使用操作唯一 ID 持久化意图；在新建 Issue 描述附加可识别的 TaskFlow 操作标记。确认创建成功后持久化平台身份；超时等结果不明时列出全部可能目标并按标记核对，查询不完整、没有匹配或多个匹配时停止并让用户核对，不凭标题或空结果自动重复创建。
- 生命周期标签固定为 `taskflow:inbox`、`taskflow:clarified`、`taskflow:promoted`、`taskflow:planning`、`taskflow:ready`、`taskflow:in_progress`、`taskflow:checking`、`taskflow:blocked`、`taskflow:done`、`taskflow:cancelled`，更新时增删 TaskFlow 阶段标签，不替换其他标签。完成与取消均关闭 Issue，重新打开任务时重新打开 Issue。缺失标签创建行为和权限必须明确告知；GitHub 与 GitLab 分别使用其原生标签接口。
- 可选只读快照和恢复意图不能写入诊断日志，不包含凭据。快照开启及位置由用户选择；默认关闭。故障导致关联更新未完成时不标记整体成功，保留已知远端身份以便恢复。
- `gh` / `glab` 作为用户显式选择远程模式的外部工具；本地模式和已有 hooks 不新增语言运行时依赖。复用或扩展仓库 JSON 处理能力时必须覆盖嵌套数组、Unicode、特殊字符及恶意输入。
## 跨工作区迁移防重
- 用户选择稳定 Todo 标记：创建前分页检查目标仓库所有 Issue，出现匹配或检查不完整时停止；不同工作区和机器不得同时迁移同一条 Todo，因为检查与创建不是原子操作。
- TaskFlow 正文编辑保留稳定标记；用户或其他客户端删除标记会削弱后续检查。标记匹配只提示人工核对，不自动合并记录。
