# Spec — 能力选择与真实问题解决调查
> Task version: v1

## Objective and Success Criteria

让 TaskFlow 各阶段在适用能力可用时更可靠地发现、评估并使用它，改善实际产物；不能用填写字段、调用无关工具或测试字符串替代行为验证。

- 开始实质工作时，引导模型将当前工作与宿主可用能力的描述匹配；有合适能力时按宿主方式读取或调用，审查结果后再吸收；没有合适能力时允许自行完成。
- 七阶段均须有可验证的引导入口和正反场景；其中头脑风暴只在目标或方向未定时展开，需求已明确的简单任务不应被迫发散。
- 对照须分别评价能力选择与产物：正确调用本身不等于调查、设计、实现或审查正确。真实场景若未达标，须继续修订，不得因静态测试通过而声称完成。

## Architecture Boundaries and Responsibilities

- 宿主事件只能证明事件到达及记录，不能单独证明能力相关、被采纳或修复成功。
- TaskFlow 负责阶段路由与有界提示；专家能力负责具体调查和规划；评估由独立的真实案例和产物检查完成。
- Codex `apply_patch` 与通过 shell / Python 写文件走不同事件路径；不得把某一工具上的门禁宣称成所有写入的强制保证。

## Project Structure / Affected Files

拟修改 `hooks/prompt-reminder` 的既有提示、`skills/taskflow/SKILL.md` 的阶段概念和能力选择说明，以及 `hooks/smoke-test` 中相关行为断言；必要时同步已声明宿主的配置与 `skills/taskflow/references/runtime.md`。复用现有 hook，不新增依赖或任务记录字段。

## Interfaces, Data Flow, and Contracts

当前机制观察：`capability-evidence` 接受 `mcp__*` 事件；`capability-gate` 按队列先后匹配阶段。事件与阶段意图及产物贡献没有一一对应，允许 unaided，审批检查审查字段完整性而非结论正确性。不能将这些机制视为真实能力选择或问题修复的证明。

候选实现契约：继续使用现有 `UserPromptSubmit` 提醒，在 planning 和执行／检查时要求模型结合当前工作内容检查宿主实际能力描述，评估是否适用；选择使用时先按宿主方式读取或调用，再将经过审查的有用结果融入当前任务。提示应允许无适合能力时自行完成，不指定供应商、技能名称、调用数量或额外审批字段。规划状态不得假定当前一定是 Spec；执行／检查状态不得假定每一轮都进入新阶段。选定能力或调用记录不代表结果可靠。

技能阶段表补充足以匹配规格编写、方案探索、实现、测试／审查和归档文档等实际概念的描述，同时保留 TaskFlow 的七阶段与固定文档结构。不得让规划能力的默认文件位置覆盖 TaskFlow 事实源。

规划技能默认输出 `tasks/plan.md`；TaskFlow 把任务目录的 `plan.md` 作为事实源。采用技能的方法时将有效内容纳入 TaskFlow 的指定文档，保留被 hooks 匹配的标题和字段，不另造竞争文档。

## Invariants and Compatibility

不从任意事件推断模型内部动机；不声称所有宿主事件行为相同；不改变仓库外的个人配置。未获真实效果证据之前，不把提示或强制字段作为最终修复。

## Validation and Error Semantics

基线包括本次遗漏能力的真实会话与 digdig 原始案例。后续受控实验要固定任务、模型、工具可用性、提示和宿主，比较具体任务的能力选择、根因证据、计划可执行性与产物；必须记录实际调用、提示到达、错误、结果和盲评口径。至少包含无需外部能力的简单对照，不能强迫所有任务调用技能。一次提示主动要求读技能的运行不构成引导效果验证。

本任务自身的 Spec 首稿遗漏了可用的 `agent-skills:spec-driven-development`：在用户指出后才读取。行为评估须覆盖复杂规格任务中对适用技能的发现、评估、读取及方法在 TaskFlow 标题下的实际运用，同时检查规格的成功标准、边界与验证方法；安排无需此技能的简单反例。技能调用和 unaided 声明本身均不足以证明结果。

逐阶段检查需求定义、研究、设计、规划、实现、验证审查和完成归档的现有引导及能力匹配。头脑风暴归属需求定义：目标或方案未定时比较可行方向与取舍；用户已确定方向时不重复发散。已读取的 `idea-refine` 适用于模糊想法和方案压力测试，不适用于方向已确定只需写规格的情况；其默认独立输出位置与 TaskFlow 事实源应分别处理。现有 smoke test 仅验证 `divergent exploration` 的声明/对账，尚无证据表明它验证实际发散质量或真实能力选择。

用户于 2026-11-12 知悉无法完全隔离后的风险，允许使用本机 Codex 真实测试：指示模型仅读取测试仓库及必要技能，监控工具调用，发现越界时中断；读取结果可能发送给 OpenAI。普通 read-only 沙箱仍允许读取本机记忆，不能作为隔离证明；不得将测试描述为完全隔离。不得主动读取或输出凭据。

## Code and Test Constraints

定向测试事件形状与脚本入口，真实行为测试必须独立于标记字段；所有夹具保留或按用户许可清理。

沿用仓库 Bash 和现有测试，不新增依赖；实施后运行 `bash hooks/smoke-test <项目内测试夹具目录>`、`python evals/runner.py`、`git diff --check`，以及仓库要求的 TaskFlow skill 校验。全量跨平台检查以 PR CI 为准。测试产生的文件按用户授权清理，不删除其他文件。若某项受环境限制不能运行，须记录原因，不能写成通过。

真实行为对照矩阵：需求定义的模糊想法与已选方向、研究中确需外部证据与不需要外部检索、复杂 Spec 与简单改字、跨文件 Plan 与简单任务、实现中有适用技术能力与无适用能力、需要审查／测试与无需额外审查、需要持久决策记录与普通归档。每项至少记录任务与能力目录、提示是否实际到达、调用顺序与结果、产物及可证伪的质量标准；正例须能检出适用能力被遗漏或调用无贡献，负例须能检出多余发散或被迫调用。优先复用历史失败样本与已获得用户同意的真实宿主测试；记录运行失败和样本限制。不能只比较调用次数或自行填写的标记。

## Design Decisions and Alternatives

- 推荐候选 A：在现有提示中增加基于当前工作内容匹配实际能力描述的明确动作，并完善阶段概念。规格、审查和头脑风暴各一次对照均观察到读取适用技能，但其中两组未证明产物质量改善；因此这只是有初步证据的设计，必须通过上述真实行为和产物验收。
- 候选 B：提高调用和阶段的对应准确性。合成事件已证明现有记录存在错配；但单独加强记录不能证明调用有用，不作为本次主要修复。若实施发现它影响可见事实的正确性，须单独设计能由宿主事件支持的最小修正，不伪称阶段或成功状态。
- 候选 C：改变模型与流程交互，把确定性操作交给程序。现有证据不足以确定更大改造的所有权和收益，暂不采用。
- 不新增硬门禁或强制命名技能；保留合理 unaided 路径。现有门禁的事件误归属与 shell 写入覆盖限制须如实说明，不以提示修订宣称它们已经解决。
