# A16 否决记录 — 「Step 必须有可核验证据」

> 2026-10-30，用户在看完实测后裁定：只查这个没有意义，不做。

## A16 的原话

> 一个 `- Status: done` 的 Step **必须带可核验证据**，否则 `completion-gate` 拒绝并点名是哪个 Step。证据的形态由 Spec 决定，但必须满足：手写能提供、`progress` 也能提供、且**不能只靠再写一行声明**。

## Spec D1 给出的形态

```
## Verification / Review 段内存在一行，包含 `Step <N>` 且 N 是该 Step 的编号
```

D1 的判定表否定过另外两种形态（固定文字、验证段非空），理由是它们查不出「验证过」与「写了句话」的区别，并把这一条列为选定形态的入选理由。

## 实测一：它被一行声明满足

`evidence-a16-fake-plan.md` 是一个**三个 Step 什么都没做**的 Plan，只在验证段写了三行 `ok`：

```
### Step 1 — 修掉并发写
- Status: done

## Verification / Review

- 2026-01-03 Step 1: ok
```

按 D1 的判定跑，结果是 `PASS — all 3 done Steps evidenced`。

**D1 自己的入选理由当场不成立。** 这个形态和它否定掉的两种一样，只要求「写一句话」，而且要求的是一句格式特定的话——比「验证段非空」还多一道格式手续。

原因不难看出：`hooks/task progress` 写的是 `- <date> Step <N>: <text>`，而这条规则只检查「有没有一行包含 `Step <N>`」。手写一行同样的文字，字节层面完全一样。**任何只读 Plan 文件的检查都无法区分二者**，因为二者在文件里就是同一个东西。

## 实测二：它对历史任务的覆盖面

93 份归档 Plan：

| 口径 | 合格 | 不合格 |
|---|---|---|
| 全部 93 份 | 20 | **73** |
| 其中走过 `progress` 的 24 份 | 17 | **7** |

D1 的判定表写着「`progress` 已经这样写……因此走 `progress` 零改动即满足」。**实测 24 份里 7 份不满足**——因为走 `progress` 的任务通常只对部分 Step 用了它（`2026-10-27-close-step-status`：Step 2 有 progress 指纹，Step 1/3/4 手写 `done`）。

所以这条规则量的不是「有没有验证」，而是「验证记录有没有按 Step 编号组织」。73 这个数字说明后者是一种少数书写习惯，不是多数。把它变成强制，等于要求每个任务收尾时逐个 Step 补一行编号——**换取零检测力**。

## 结论

A16 不做。理由不是「成本高」，而是**它做不到自己承诺的事**：D1 明确说目标是区分「验证过」与「写了句话」，而实测证明这个形态恰恰只需要写句话。PRD 风险表预置了这条判据：

> 若 Spec 给不出一个真能区分「验证过」与「写了句话」的形态，正确做法是**缩小承诺**并在 PRD 里改 A16，而不是实现一个查不出东西的检查。

## 保留的部分

- **A17 照做**：同一 Step 块两个 `- Status:` 行报错。那是文档自相矛盾，判定是确定的，不依赖任何关于「真假」的判断。
- **R11/R12 不变**：不强制 `progress`。
- **A15 仍然要证明**：`progress` 写的与手写的判定必须一致。现在这条更容易成立——因为没有任何检查会读它们。
- **事实 5 的诊断不变**：`progress` 是少数路径，机制原因是它只增摩擦、无可验证产出。本记录是那个诊断的又一次确认，不是它的反例。

## 若将来要重做

要让「验证过」与「写了句话」可区分，唯一的方向是让 `progress` 写出**机器无法伪造**的东西——例如带上 capability store 的序列号，或由若干次真实工具调用派生。那需要一个新的设计，不是把 A16 换个措辞。记录在此，不在本任务范围内。
