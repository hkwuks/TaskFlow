# Changelog

## [Unreleased]

### Fixed

- **A Step counts as closed only when it says `- Status: done`, so a word the gate did not know can no longer archive a Plan that is not finished.** `hooks/completion-gate` read the field as a blacklist — `pending`, `in_progress`, `blocked` were named and everything else was finished — so the word `completed`, a misspelling, an empty value, and a Step with no `- Status:` line at all all passed. Measured 2026-10-27 by driving the gate directly: `completed`, `complted`, `skipped`, `wip`, `DONE`, an empty value and a missing line each returned exit 0 and "finished". `hooks/task progress` has only ever accepted `pending|in_progress|done|blocked`, so those spellings could not have been written by the tool — they are the result of hand edits made precisely because the two sides disagreed. Closed is now a whitelist of one word, and it is the same word the writer accepts. The block is located by its `### Step <number>` heading anywhere in the Plan rather than only under `## Steps`, because that is how `task progress` finds the block it edits; a reader that skipped the other sections would see a different set of Steps than the writer changes. **Knowingly still open, and pinned by an assertion so it stays a decision**: a Plan with no `### Step` block at all is not refused, because "must a Plan have Steps" is a separate rule this change does not make.
- **The Windows smoke suite no longer stops dead when its stdin is open and silent.** `hooks/smoke-test-windows.ps1` called `run-hook.cmd session-start` with no stdin of its own, so the hook inherited the runner's — and `session-start` reads its event with `cat`. From a terminal that read never reaches EOF, so the suite printed `WINDOWS LAUNCHER ARGS PASSED` and then hung indefinitely; a red assertion reached a person as an unexplained freeze rather than a message. The cause is the inherited stdin, not the throw the report named: probing with `throw` at eight positions, every one before that call printed and exited 1 in under 14s, while every one after it hung — the boundary is exactly `Invoke-SessionStart 'pr'`. The bash suite already carried this lesson for its own `session-start` call (`hooks/smoke-test`, `< /dev/null`); the PowerShell one is now given an empty event the same way, through `cmd /c "... < nul"` rather than `'' |`. **An empty PowerShell string is not an empty stdin** — it is encoded and written as a line, and which line depends on `$OutputEncoding`: measured 0x0d 0x0a on the author's machine and a BOM on the CI runner, where `session-start` rejected it as invalid JSON and the suite failed ([run 40712165629](https://github.com/hkwuks/TaskFlow/actions/runs/40712165629)). A redirection is zero bytes on every host. Measured 2026-10-28: before, still silent at 180s and killed; after, four `PASSED` banners in 27s. **CI could never have caught it** — a runner's stdin is empty, so `cat` sees EOF at once and every windows-latest job has been green regardless.
- **The Windows suite now checks this itself, by re-running with an inherited open stdin and failing if it does not finish.** The check has to live there rather than in `hooks/smoke-test`, because that suite does not run on the Windows runner at all — the workflow gates it on `runner.os != 'Windows'` — so an assertion written there is skipped by every CI job, and the one platform that can reproduce the defect is the one platform that never executes the check. `hooks/smoke-test-windows.ps1` is the only TaskFlow check a Windows runner runs, which makes it the only place this can be caught automatically. It spawns itself with `RedirectStandardInput` set and never written: a pipe that is open and silent, the shape a terminal gives a command a person typed and the shape CI does not have. `TASKFLOW_STDIN_SELFCHECK` bounds the recursion to one child. Verified by mutation: with the `session-start` call reverted to inheriting, the child is killed at the 90s deadline and the suite fails naming the read; with `< nul` in place it exits 0 in about 28s, and the whole suite takes 51s.
- **`hooks/smoke-test-windows.ps1` must stay 7-bit ASCII, and now asserts it.** Windows PowerShell 5.1 reads a `.ps1` with no BOM using the system ANSI code page rather than UTF-8, so a literal non-ASCII character is decoded into bytes the parser does not expect: measured 2026-10-28, an em dash in a `throw` message arrived as three UTF-8 bytes, the third swallowed the closing quote, and the whole file failed to parse with "The string is missing the terminator" ([run 40717070366](https://github.com/hkwuks/TaskFlow/actions/runs/40717070366)) -- after the suite had passed on Linux and macOS, which read the same bytes as UTF-8. The file was already ASCII-only for this reason and builds its Chinese fixtures from `[char]` codes; the rule was known and unenforced. The first thing the suite does now is read itself and refuse to run if any non-ASCII character is present, naming the line and code point. Verified by mutation: injecting one em dash makes it fail at the guard.
- **The same inherited stdin reached one more `session-start` call, in `hooks/smoke-test` itself.** Its `== Windows launcher finds Git Bash ==` section ran `cmd.exe //d //c ... session-start` with no stdin, so it had the identical failure mode: measured 2026-10-28, it never returned against a held-open stdin and returned at once with `< /dev/null`. Given the empty stdin it now has, the same way and for the same reason.


### Compatibility

- **Five archived Plans read as unfinished under the new rule, and are not rewritten.** `achieved/` is read-only in place, so nothing here changes them and no task is blocked by them. They are: `2026-09-07-repository-standards-and-doc-root` (three Steps say `done (v1)`), `2026-10-11-gate-host-coverage` (four say `completed`), `2026-09-08-token-efficiency` and `2026-09-14-personal-docs-git-boundary` (their Steps still say `pending` while the Plan header says `completed` — the same disagreement running the other way), and `2026-10-22-taskflow-drift-guard`, whose `## Verification / Review` section reuses `### Step 1` as an ordinary subheading for a table. Recorded rather than repaired: editing history so it passes a check that no longer applies to it would make the record say something untrue. Only two of the five change verdict when the real gate is run over all 91 — the other three were already refused on `main` for reasons that have nothing to do with Steps, so this release does not newly refuse them.

## [1.1.9] — 2026-10-26

### Added

- **`hooks/task recover` repairs a capability store instead of requiring it to be thrown away.** `consumed` is the highest sequence in `released` and the queue length is counted in `evidence`, so a store whose evidence was truncated or deleted reads as further along than it is: the gate denies every stage, `unaided` refuses to widen the gap, and `approve` now refuses too. The only recovery was `rm -rf` on the whole store, which discarded every release whose record still existed along with the ones that had none. The repair is arithmetic rather than reconstruction — a release at a sequence past the end of `evidence` points at a record that is gone, and that is the only kind identifiable without guessing — so `recover` drops exactly those rows, keeps the rest, and appends what it dropped to `released.discarded`. It never adds a release and accepts no argument naming rows, because a command that could write a release would be a way to edit the ledger. A healthy store is a read-only no-op: nothing is written and no discard file appears.

### Fixed

- **A release record now names the task that earned it, so two tasks at the same version no longer share one.** `released` was keyed on `(version, stage)` alone. Two tasks at the same `> Task version:` in one store — which happens whenever a second task starts in a worktree an earlier one used, and the store lives in the worktree's git dir — therefore meant the second task's stage was satisfied by the first task's row: the gate allowed the write, wrote no line, and spent no evidence. Measured 2026-10-26: task A released `PRD` at `v1`, task B (also `v1`) wrote `prd.md` and the gate allowed it while `released` stayed at one row and `evidence` still held an unspent record. A row is now `<task>|<version>|<stage>|<seq>|<kind>|<capability>`, and the gate's skip, `unaided`'s idempotence, and `approve`'s reconciliation and invoke pool all key on the task name as well. `consumed` deliberately still reads both line shapes — it answers "how much of the queue is spent", which has nothing to do with which task spent it — so upgrading does not turn old sequences back into unspent ones and release evidence a second time.
- **`hooks/task approve` accepts any of a stage's `- [Stage]` lines, not only the first.** The section is specified as a report of what happened, and one phase can invoke more than once; reading only the first line refused an honest report because the recorded name happened to be on the second one. Measured 2026-10-26 on a Plan with two `- [Plan]` lines, the recorded capability on the second: `stage [Plan] does not name a capability invoked in this Task version`. Every line is now considered, and the four distinct refusals — invocation-shaped over an unaided record, a missing `considered:`, a mismatched class, and a name no invocation produced — keep their own wording, because the fix differs for each.
- **`hooks/task approve` refuses a capability store whose releases outrun its evidence.** It reconciled each stage against `released` by `(version, stage)` alone, so a release whose sequence pointed at a record that no longer existed still counted. Measured 2026-10-25: with `released` at seq 4 against 3 evidence lines, `approve` wrote `approve OK (user, v1)`; deleting that one row made the same document fail with "stage [Test] was never released by the pre-write gate". Whether a task could be approved therefore depended on damage to the store. The check runs before any Approval field is written, uses the same sequence arithmetic the gate and `unaided` use, and names `recover` as the repair.
- **The gate's out-of-step denial names `recover` alongside the two recoveries it already listed.** The wording said "two ways forward" and both of them had a cost: producing the missing records spends calls, and deleting the store discards the releases. The repair it now names first keeps every backed release and re-declares only the stages it had to discard. No condition in the gate changed.
- **The eight `sessions.md` copies that were already tracked are out of the repository.** 1.1.8 made `sessions.md` and `personal.md` clone-local by writing an exclude rule into each clone's `.git/info/exclude`, and the rule works: measured 2026-10-25, a task directory holding both `prd.md` and `sessions.md` stages only `prd.md`. But a rule applies to untracked paths, so the copies already in the index kept travelling — stale on every other clone, and visible in `git status` as somebody else's session record. All eight predate the rule (the last was added 2026-10-24, one day before it landed), none was force-added, and all eight are under `achieved/`. They are removed from the index and kept on disk unchanged; history is not rewritten. **The one way this can lose work**: a clone that had edited one of those copies sees a deletion and an ignored untracked file, so its edits do not surface as a conflict. Nothing in this repository edited them after archiving, but another clone is not something this repository can check.

### Compatibility

- **One deliberate break: a `released` row written before this version no longer releases anything.** Those rows are five fields and record no task, and the task that wrote one cannot be inferred — the guess "whichever task is active now" is the mistake this change removes, and it was measured wrong on 2026-10-26 (`unaided` named a different task's directory). So they are not migrated, not guessed at, and no compatibility layer makes them work: they are reported as belonging to no task, with the one-time clear (`rm -rf <absolute-git-dir>/taskflow`) named in the refusal, and a task that has one is unblocked by declaring its stages again or re-running the phase. Their sequences are still counted, so nothing is double-spent. A row whose field count is neither five nor six is damage rather than an old format and is refused as such. On a fresh worktree there is no store, and this break never comes up — the repository's own base checkout has none.
- **No install command changes, no rename, and no hook gains an interpreter dependency.** The four manifests keep their shape, every `hooks-*.json` wiring file is untouched, and the new code is `git`, `awk`, `sed`, `grep`, `tr` and POSIX shell builtins.

## [1.1.8] — 2026-10-25

### Added

- **Writing the tests is a recorded stage, and `hooks/task unaided` accepts `Test` as a fourth stage.** The phase table has named `testing strategy and code review` for as long as it has existed, and nothing carried it: the pre-write gate releases `prd.md`/`spec.md`/`plan.md` on their first body write, `unaided` accepted those three names only, and `approve` asked about those three only. Measured 2026-10-24: 77 of 85 archived Plans ran tests and none recorded the phase. `Test` is now required of every task — there is no test document whose existence could decide it, and inferring one from a Step's wording would be a second standard for what counts — so a task that wrote no tests declares that in one line.
- **A `Test` declaration spends a standing evidence record instead of writing its own.** Every other stage is released by the gate, which consumes the evidence queue when it sees a document's first write; a stage whose artifact is many files across several Steps has no such moment. `hooks/task unaided Test` therefore does what the gate would have done: if the evidence file holds an unreleased line it spends that line and records an invocation naming it, otherwise it records an unaided declaration. **The kind follows the queue, not the caller** — a declaration decides which concept class applied and can never assert that a call happened. It prints which of the two it wrote, because the `[Test]` line has to agree with the record and the release store is not a file anyone is meant to read.
- **A Plan can declare material that must come back while the task runs, and `hooks/prompt-reminder` prints it every prompt.** The routed document list is produced at SessionStart and injected once, so in a long implementation the Agent works from whatever it read at the beginning — and `## Reference Pointers` listed what had been consulted without anything bringing it back. A bullet written `- [Reinforce] \`path\` — reason` inside that section is now a declaration: the hook prints the paths on one line between the in-flight task line and the classification question, in Plan order and once per path. Admission needs the marker, a backticked path, the `—` separator and a non-empty reason; a line missing any of them is dropped rather than parsed as far as it goes, because a malformed bullet reported as a pointer says a document is missing when the bullet is what is wrong. The path has to be a POSIX repository-relative one and is trimmed first: a leading `/` or `~`, a backslash, a colon, or any `..` segment is dropped, since the hook cannot resolve it and an unresolvable entry would be a claim rather than a fact. Fenced blocks are skipped, because the Plan outline in `artifacts.md` is itself fenced and contains the heading verbatim.
- **A reinforce pointer whose path no longer resolves prints as `MISSING:` instead of disappearing.** Material going missing is the failure the list exists to surface, so filtering it would make the reminder quietest exactly when it had most to say. The shape follows the index's existing treatment of a missing catalog entry rather than inventing a second vocabulary.
- **The suite asserts the reinforce line's admission rule, its position and ordering, and the output that preceded it.** Sixteen cases, including every shape a review measured printing as a `MISSING` document rather than being dropped — a trailing `..` segment, a Windows drive path, a UNC share, a scheme with no `//`, an untrimmed path, a whitespace-only path, a reason carrying a backtick, and an example inside a fenced block.
- **The suite now checks that the two documents inventorying `hooks/` still match the directory.** `hooks/README.md`'s tree and `runtime.md`'s §Folder layout are both prose listings of the same 29 entries, and neither was checked against `ls hooks/` — so both had drifted silently. Measured 2026-10-24: the README tree was missing `repository-check`, and `runtime.md` named neither it nor `release-version`; both are documented in `RELEASE.md`, so the knowledge existed and simply was not in the file each reader is routed to. The assertion compares both directions — a file nobody lists, and a listing naming no file — and only names, not descriptions, because a line can name a script and still describe it wrongly.
- **TaskFlow's clone-local files are excluded from `git status` by the plugin, without the user editing `.gitignore`.** `TaskFlowDocs/repository-docs/personal.md` (a personal rule, never team policy) and `sessions.md` (a session id, a working directory, `Session availability: local-only`) were both documented as never committed, and nothing made that true outside this repository: the `.gitignore` rule that happens to cover `personal.md` is there for `index.md`'s sake, and eight `sessions.md` copies had been committed before anyone noticed. `hooks/install-git-hygiene` now writes `TaskFlowDocs/repository-docs/personal.md` and `TaskFlowDocs/**/sessions.md` into the clone's own `.git/info/exclude`, which is the per-clone place for a per-clone rule — a tracked `.gitignore` line would have changed every clone's view, including a clone that does want to commit those paths. The rule hides only untracked paths: Git applies no ignore rule to a tracked one, so a copy forced in once keeps showing in `git status` rather than going quietly stale. Those eight copies stay tracked until `TF-20261025-24d06c` clears them.
- **An achieved task's root Task version must have an `old/vN/` for every version below it.** This is the half absorbed from `TF-20261008-4d37b2`. `hooks/version` writes `old/vN/` before bumping to `vN+1`, so a gap means a superseded version was overwritten in place and the recovery procedure has nothing to restore. Measured 2026-10-24: all 83 achieved tasks, 0 gaps — a regression guard rather than a repair.

### Fixed

- **The pre-write gate no longer reports a broken capability store as a spent invocation.** `consumed` is the highest sequence in `released` and the queue length is counted in `evidence`, so a store whose evidence was truncated or deleted reads as further along than it is. The gate reported that as "the most recent invocation was already spent by an earlier document" — a false statement, since the sequences it counted as spent had no record behind them, and a remedy that cannot work, since no single invocation closes a gap of five. Measured 2026-10-25 with `released` at seq 5 and an empty `evidence`. It now names the two numbers, the size of the gap, and both recoveries with their costs: produce the missing records, after which the gate releases again and every release already written survives, or delete the store and declare each stage again, which discards them. The two sound states — a queue already spent, and a store with nothing banked — keep their wording byte for byte, and the gate's release condition is unchanged.
- **`hooks/task unaided` refuses a capability store whose `evidence` is already behind `released`, instead of writing into it.** Both writers take the next sequence from `released` alone, so a store whose evidence file was deleted or truncated reads as further along than the queue actually is; every declaration then widened the gap, and the gate denies every stage from that point on with nothing that can close it. Measured: `released` at seq 3 with no `evidence` file, one `unaided` call, `released` at seq 4 against 1 evidence line. The declaration now fails and prints both numbers; the records cannot be rebuilt, so the message names the recovery — delete `<absolute-git-dir>/taskflow` and declare each stage again.
- **`hooks/smoke-test` no longer blocks on its own stdin.** Two cases run `session-start` without feeding it an event, and `session-start` reads its event from stdin by contract — so inheriting the suite's stdin made the read wait for whoever ran it. Measured 2026-10-25: `bash hooks/smoke-test` from an interactive shell stopped after the first `session-start` case for more than 145 seconds, and under a runner that holds the pipe it hangs indefinitely. Both now redirect `< /dev/null`; they mean "no event", not "read the caller's terminal".
- **`hooks/README.md` and `runtime.md` name `repository-check` and `release-version`, and say where their procedure lives.** Both are release-procedure commands rather than lifecycle ones, which is why they were left out of the lifecycle tables — but `runtime.md` is also where a reader is routed for the `hooks/` layout, so leaving them unmentioned made two existing commands invisible from the one file that describes the directory.
- **`hooks/completion-gate` is the one rule for "approved and finished", and both entry points into `achieved/` ask it.** Four commands need this answer and three of them answered it separately. `hooks/archive` checked nothing but the two `> Status: completed` lines; `hooks/task complete` checked three conditions; `task state in_progress` and `task progress` checked the approval half. The copies had begun to disagree, and the two entry points did not defend the same thing. Measured 2026-10-22: with the `## Approval` block emptied, two Steps left `pending` and an unchecked item in the Plan, hand-editing the two `> Status:` lines and running `archive` printed `archive OK` and exited `0`. The rule now lives in one file, called the way `hooks/archive` already calls `task-id`, and `archive` reaches it before the directory moves, so a refusal leaves the task active, the Todo unchanged and `achieved/` without it. Seventeen of 82 archived Plans fail the rule and stay untouched — they predate it and are read-only history; the gate never runs on them.
- **A `printf | grep -q` test disabled itself on any Plan larger than the pipe buffer.** `hooks/task complete` read the Plan into a variable and tested it through a pipe under `set -o pipefail`: `grep -q` exits on the first match, `printf` takes SIGPIPE and dies with 141, and `pipefail` reports the whole pipeline as failed — so the guard was skipped. Measured on the pre-existing code, a 111 KB Plan with an unchecked item first in the file was archived **15 times out of 15**, and the same shape falsely refused a genuinely approved 39 KB `## Approval` block **16 times out of 200**. `completion-gate` reads the Plan as a file in a single `awk`, which is exact at any size. The suite had passed with the defect present, so both sizes now have fixtures.

### Changed

- **`hooks/install-merge-driver` is now `hooks/install-git-hygiene`, and it writes one more thing.** The name stopped describing the file once it also wrote the two exclude rules, and a second hook writing into the same `.git/info/` would have made "which one sets my exclude" a question. It now writes the Todo merge driver, the `merge=taskflow-todo` attribute, and both exclude rules, in that order, stopping at the first failure as before. Anyone with `hooks/install-merge-driver` in a script or a local note has to rename it; the file no longer exists under the old name, deliberately, rather than shipping an alias that would keep two names alive.
- **`task approve` now requires a `[Test]` stage line, and refuses a Plan without one.** This is a deliberate break, not a compatibility gap: leaving the stage optional is what let it go unrecorded for 85 tasks. The refusal names the one command that supplies it, `bash hooks/task unaided Test --considered 'testing strategy'`, so an in-flight task is one line from unblocking. Existing tasks are not backfilled — `achieved/` is read-only history and `approve` never runs on it.
- **Phase 7 names `hooks/task complete` as the archive transaction, with the manual sequence described as what it performs.** `skills/taskflow/SKILL.md` previously stated the hand sequence — mark the documents `completed`, move the directory, close the Todo entry — as *the* procedure, and named `complete` only in the preferred-command list, which is exactly the path that bypassed the gates.
- **`task state in_progress` and `task progress` keep their mid-task behaviour through `--approval-only`.** They must not require a finished Plan — that is what they are working towards — so the shared file answers the narrower question for them rather than gaining a second copy.

### Compatibility

- **One deliberate break, and it is cheap to satisfy.** `task approve` now refuses a Plan whose `## Skills / Tools Used` has no `[Test]` line. A task that is mid-flight when this lands is unblocked by one command, `bash hooks/task unaided Test --considered 'testing strategy'`, which the refusal itself names. Nothing else about an in-flight task changes: the other three stages reconcile exactly as they did in 1.1.7, and `achieved/` is never re-validated because `approve` does not run there.
- **One rename with no alias, on purpose.** `hooks/install-merge-driver` is now `hooks/install-git-hygiene`. A script, local note, or global settings file that names the old file must be updated; the old name no longer exists, rather than shipping an alias that would keep two names alive. `hooks/session-start` calls the new name itself, so an install that relies on the hooks needs nothing.
- **No install command changes, and no hook gains an interpreter dependency.** The four manifests keep their shape, every `hooks-*.json` wiring file is untouched, and the new code is `git`, `awk`, `sed`, `grep`, `tr` and POSIX shell builtins. The suite still installs no language runtime on any of the three hosts.
- **`sessions.md` and `personal.md` stop appearing in `git status`, but only where they are untracked.** The exclude rules live in each clone's own `.git/info/exclude`, written by `hooks/install-git-hygiene` at SessionStart. Git applies no ignore rule to a tracked path, so the eight `sessions.md` copies already committed stay visible and are tracked until `TF-20261025-24d06c` clears them; a clone that deliberately commits one keeps seeing it change.
- **A desynced capability store is now reported as desynced, and nothing about it is repaired.** The gate's release condition, the shape of `evidence` and `released`, and every write are exactly as they were in 1.1.7. What changed is the message: it names the two numbers and both recoveries instead of calling the store a spent invocation. A store that is already desynced behaves as it did — every stage denies — and the message now says why.

## [1.1.5] — 2026-10-11

### Fixed

- **A stage can now be released on a host that has no pre-write gate (PR #80).** `hooks/task approve` reconciles every required stage against `<absolute-git-dir>/taskflow/released`, and the pre-write gate was the only writer of that file. Three of the five supported hosts wired no tool-call event at all, so on those the gate never ran, `released` was never created, and `approve` refused forever — printing, as its remedy, the very `hooks/task unaided` command that could not work. Since `approve` is the only sanctioned writer of the Approval block, `in_progress`, `complete`, and the archive were all unreachable there, and the only way forward was to hand-write an approval the gate would then accept. `hooks/task unaided` now writes the release record itself, so a declaration releases its stage on any host, with or without a gate. Both lines are always written together and in that order — the gate releases a stage when the evidence holds more lines than the highest sequence already released, so a release without its matching `evidence` line would put `consumed` above the evidence and deny every stage from then on. ### Added

- **CodeBuddy is a gated host (PR #80).** `hooks/hooks-codebuddy.json` gains `PreToolUse` (`Write|Edit`) and `PostToolUse` (`Skill|Agent|Task`, `mcp__.*`), running `capability-gate` and `capability-evidence` unchanged — no hook script gains a host branch, the same contract-match discipline Trae was wired under. The contract was read out of the packaged CLI (`@tencent-ai/codebuddy-code@2.137.0`) because CodeBuddy's own two documentation surfaces disagree: its CLI hooks reference names the write tools `Write`/`Edit` and reads `tool_input.file_path`, while a second, older surface names them `write_to_file`/`replace_in_file` with a camelCase `filePath`. The shipped bundle settles it — the tool-name enum carries `WRITE="Write"` and `EDIT="Edit"`, `PermissionUtils` reads `file_path` for both, and MCP tools are built as `mcp__<server>__<tool>`; the lowercase spellings reach the bundle only as telemetry aliases that collapse to the same metric key, never as an event's `tool_name`.

### Changed

- **`hooks/task unaided` changes meaning on every host, not only on gate-less ones.** Previously a declaration registered the phase but the gate released it, at document-write time; now the declaration releases it immediately. The user-visible result is the same — the stage is released and the document is writable — but a declaration now leaves a release record even when no document follows, which is exactly the record `approve` reconciles against. `hooks/task unaided` still records an explicit declaration, never a disguised invocation, so the gate's boundary is unchanged: it still refuses every write with no record behind it.
